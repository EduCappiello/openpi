## Two-stage architecture (STAR warm-start — critical)

```
wave8_d90_100  ──────────►  backbone_foundation          (Stage 1, 32 tasks)
                                 │          │          │            │
                    F4_heavy_grasp  F3_surface_contact  F2_actuation  F1_constrained
                    (8 tasks)       (13 tasks)          (25 tasks)    (26 tasks)
```

- **Stage 1** — `pi05_b1k_backbone_foundation` warms from
  `outputs/checkpoints/pi05_b1k_wave8_d90_100/wave8_d90_100/14999/params`.
- **Stage 2** — each expert warms **directly** from the completed
  `backbone_foundation` checkpoint
  (`outputs/checkpoints/pi05_b1k_backbone_foundation/backbone_foundation/14999/params`).
- **Do NOT chain experts** (`F4→F3→F2→F1`): sequential chaining causes
  catastrophic forgetting and cross-family skill corruption. The warm-start graph
  is a star, enforced in `_make_family_configs()` in
  `src/openpi/training/config.py`. Override per-run via `B1K_FAMILY_WARM_START_PARAMS`.

## Config

Every stage is **full fine-tune `pi05`** (`action_horizon=32`, `gemma_2b` — no LoRA,
`fsdp_devices=2` on this 2-GPU pod), batch size 32, 15,000 steps, cosine LR decay to match,
`keep_period=save_interval=2500` final step pinned, `val_log_interval=2500`,
`num_workers=8`. Normalization stats are shared from the wave assets
(`outputs/assets/pi05_b1k`), so **no norm-stats recompute** is needed. Configs are
auto-generated by `_make_family_configs()`.

> **2-GPU caveat:** batch 32 on 2 GPUs sees half the per-step data of the original 4-GPU
> batch-64 run at the same 15,000 steps; double `num_train_steps`/`decay_steps` if data
> coverage matters for a re-run.

Generated config names: `pi05_b1k_backbone_foundation`,
`pi05_b1k_F4_heavy_grasp`, `pi05_b1k_F3_surface_contact`,
`pi05_b1k_F2_actuation_transfer`, `pi05_b1k_F1_constrained_insertion`.

## GPU memory handling (auto, in `preflight.py`)

Training needs ~47–49 GB free/GPU on this pod (`XLA_PYTHON_CLIENT_MEM_FRACTION` ≈ 0.60 on an
80 GB H100). `preflight.py` computes it from live VRAM:

```
FRAC = (MIN_FREE_MiB − B1K_MEM_SAFETY_MIB) / TOTAL_MiB      # safety default 4096
FRAC = min(FRAC, B1K_MEM_FRACTION_CAP)                      # cap default 0.85
abort if FRAC < B1K_MEM_FRACTION_FLOOR                      # floor default 0.59 (this pod)
```

**This pod's floor is tuned to 0.59** (`B1K_MEM_FRACTION_FLOOR`, in
`preflight.py`): with ollama holding ~28.7 GB/GPU the best achievable fraction is
(81559 − 28666 − 4096)/81559 ≈ 0.593, so the floor must sit below that or every run FATALs.
Proven working: 0.593 with ollama resident, ~49 GB preallocated, batch-32 full-FT.

- **Full-FT + FSDP:** the model is `gemma_2b` full fine-tune with **`fsdp_devices=2`**
  (this 2-GPU pod), which shards the 2.4B model + fp32 Adam optimizer states across the 2
  GPUs — per-GPU footprint ≈ 50 GB at batch 32 (verified 2026-08-27).
- Manual override: set `B1K_MEM_FRACTION`.
- **VRAM hogs.** This pod runs the agent's **ollama** (`ollama serve` + its child
  `/root/lib/ollama/llama-server`, ~28 GB/GPU while a model is loaded). **Keep ollama
  running** — training is tuned to run alongside it (that's why the floor is 0.59). If you
  must free VRAM, stop it yourself (`kill <llama-server pid>`); never `pkill -f ollama`
  blindly. At fully-free GPUs preflight yields the 0.85 cap — raise the fraction if you do.
- Do not lower the floor below ~0.59: preflight would pass but XLA would preallocate too
  little and training would OOM mid-run.
- Env: `B1K_MEM_SAFETY_MIB`, `B1K_MEM_FRACTION_CAP`, `B1K_MEM_FRACTION_FLOOR`,
  `B1K_MEM_FRACTION`.

## Failure / resume semantics

- **Idempotent + crash-safe**: the orchestrator re-derives state from disk each
  iteration and can be killed/restarted any time.
- **Verify from disk, not exit code**: `family_status.py --check <name>` checks
  `{checkpoint_dir}/14999/params` exists; a caught exception in `train.py` can
  still exit 0.
- Every training launch uses `--resume`, which is safe unconditionally: an empty
  checkpoint dir means fresh warm-start from the warm-start params; a partial dir
  resumes that run.
- Uploads are **non-fatal**; checkpoints are kept locally until you explicitly
  run `cleanup_family.py --yes`. No auto-delete.

## Data staging (`stage_family.py`)

- Fetches `meta/*` first (small), then the task-filtered RGB media for a family's
  tasks in demos 90–99, in parallel with per-file timeouts and worker back-off.
  Already-local files are skipped, so overlapping dual-family tasks don't
  re-download.
- Media lives at `/root/.cache/huggingface/lerobot/behavior-1k/2026-challenge-demos` — on this
  pod that is a **symlink to `/tmp/hf-cache/lerobot`** (the big volume; `/` is a 66 GB PVC).
